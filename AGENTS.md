# internal-tools — песочница внутренних тулов

Внутренняя платформа исполнения одноразовых тулов с контрактом допуска. Здесь агенты за часы собирают UI-приложения под бизнес-процессы, не проходя продуктовый релизный цикл, потому что рамки заданы заранее и проверяются машиной.

Решения ниже приняты, не переизобретай их.

Этот файл — правила для любого агента: Claude Code (через `CLAUDE.md`), Cursor, OpenCode, Codex и других. Как подключить агента к песочнице — в конце файла.

## Первый запуск

Свежая копия репозитория — это ещё не стенд: контейнеров нет, секретов нет, тулов нет. Первое, что агент делает
в такой копии, — разворачивает её:

```bash
sh infra/setup.sh            # проверит окружение, поднимет стенд, проверит здоровье, скажет что дальше
sh infra/setup.sh --check    # только проверка окружения, ничего не меняет
```

Скрипт идемпотентен: на поднятом стенде он ничего не ломает. Он создаёт секреты локально (`.env`, в git не
попадает) и никуда их не отправляет. Человек стенда сразу входит в `sandbox-admins`, `sandbox-approvers`
и `sandbox-developers` — последняя нужна, чтобы агент получил доступ к репозиторию (шаг Б6). Чего он не делает, потому что это решения человека: не меняет пароли,
не открывает стенд в сеть (`make lan`), не создаёт тулы. Первый тул собирается через MCP-сервер `sandbox` —
как именно, ниже в «Границах агента» и «Работе над тулом».

## Четыре инварианта

Нарушение любого означает, что это уже не песочница. Если задача требует нарушить инвариант, остановись и спроси человека.

1. **Контракт допуска.** Тул попадает в контур только с валидным `tool.yaml`. CI сверяет манифест с реестром одобренных источников (`registry/sources.yaml`). Нет в реестре — сборка падает.
2. **Единственный выход к данным.** Тул не ходит в базы и внешние API напрямую. Сеть тулов видит только гейтвей. Гейтвей выдаёт токен строго под манифест и пишет аудит каждого вызова.
3. **Единый каркас.** Авторизация, доступ к данным, логирование, деплой и рендеринг UI приходят из `packages/sdk`, `packages/ui-kit` и `charts/tool-base`. Тул содержит только предметную логику.
4. **Принудительная смертность.** У тула есть `ttl_days`. Использование человеком (не агентом) продлевает срок на `ttl_days`, но не дальше `max_ttl_days` от последнего явного продления владельцем; дальше — только явное продление. Нет вызовов человека `idle_days` дней — владелец получает уведомление, и через `idle_grace_days` тул удаляется вместе с ресурсами. Молчание считается отказом.

Человек принимает решение дважды: когда одобряет источник в реестре и когда смотрит превью-ссылку. Всё между этими точками автоматично. Если для выкатки тула нужно чьё-то ручное решение, это уже не песочница.

## Контракт `tool.yaml`

```yaml
name: manager-board           # slug, совпадает с именем папки в tools/
owner: ivan.petrov                # логин человека или группа из справочника; отвечает за продление
ttl_days: 30                  # не больше лимита из реестра

sources:                      # только id из registry/sources.yaml
  - tasks-readonly
  - knowledge-readonly

writes:                       # явные права на запись, каждая требует подтверждения человеком
  - tasks.task:create
  - tasks.task:update
  - pastry.stock:adjust:      # право можно сузить до групп (шаг Б5)
      groups: [pastry-stock]

ui:
  mode: [web, mcp-app]        # витрина *.tools.localhost и/или MCP App в хосте агента

access:                       # кому открыт тул; раздела нет — только владельцу
  groups: [support-team]      # группы: из IdP или заведённые администратором
  people: [ivan.petrov]       # исключения: подрядчик, стажёр
  agents: true                # можно ли подключать тул агентом (MCP)
```

Круг доступа ограничен и со стороны данных: шире, чем `allowed_groups` источника в реестре, тул открыть нельзя —
это проверяют CI и гейтвей. Живой круг меняется на главной без передеплоя, и он главнее манифеста: при расхождении
деплоер пишет предупреждение, а не перезаписывает.

Источник, которого нет в реестре, неизвестный `writes` или `ttl_days` сверх лимита роняют CI. Чтобы добавить источник, нужно решение человека в реестре, а не правка манифеста.

## Структура репозитория

```
registry/sources.yaml     # одобренные источники: поля, чувствительность, владелец
registry/directory.yaml   # справочник сотрудников (заглушка HR/IdP): кто ушёл, руководители, группы-владельцы
gateway/                  # единственный узел доступа: реестр, токены, скоуп, аудит, MCP-эндпоинт
infra/identity/           # личность: вход через IdP, ForwardAuth, подпись X-Sandbox-Identity, личные ключи MCP
connectors/<источник>/    # коннекторы источников: сервисы команды данных за гейтвеем (сеть sources)
packages/connector/       # каркас коннектора: HTTP-протокол с гейтвеем, applyQuery, sqlSelect, ConnectorError
mcp-sandbox/              # MCP-сервер платформы для build-time агентов
portal/                   # главная http://tools.localhost:18000: каталог, страница тула, источники, здоровье, разработчику
charts/tool-base/         # общий способ собрать и запустить тул (локально: Dockerfile + compose-фрагмент)
packages/sdk/             # клиент гейтвея, типы, аудит-контекст
packages/ui-kit/          # компоненты, рендерятся и в web, и как MCP App
packages/manifest/        # схема и валидатор tool.yaml
templates/new-tool/       # скелет, с которого стартует любой тул
templates/new-connector/  # скелеты коннекторов: sql (база), api (HTTP API), mcp (MCP-сервер системы)
tools/<slug>/             # tool.yaml, src/, AGENTS.md
docker-compose.yml        # весь стенд; `make up` поднимает его одной командой
infra/                    # сид Postgres, раннер и образ CI, деплоер (deployer), уборщик (reaper), уведомления (notifier), bootstrap Gitea, demo/, agents/
publish/                  # файлы только для публичного репозитория: лицензия, README на английском, SECURITY.md
bin/sandbox-mcp           # единая точка входа MCP для любого агента
.mcp.json, .cursor/mcp.json, opencode.json   # конфиги агентов, генерирует `make agents`
.gitea/workflows/         # CI на Gitea Actions: только проверки, без секретов и Docker
```

## Границы агента

Агенты бывают двух видов, и их права никогда не смешиваются.

**Build-time агент** меняет код. Работает через MCP-сервер `sandbox` (`mcp-sandbox`): `list_sources`, `scaffold_tool`, `validate_manifest`, `deploy_preview`, `open_pull_request`, `get_logs`; для задачи на коннектор — `scaffold_connector`, `validate_connector`. Без MCP те же вызовы: `node infra/demo/sandbox-call.ts <инструмент> '<json>'`.

Можно:
- писать код внутри `tools/<slug>/src/`;
- править `tool.yaml` своего тула;
- использовать SDK и ui-kit.

Нельзя:
- трогать `gateway/`, `charts/`, `packages/`, `registry/`, `connectors/`, `.gitea/` из задачи про тул;
- добавлять драйверы БД и HTTP-клиенты к чему-либо, кроме гейтвея;
- открывать сеть, заводить секреты, писать свою авторизацию или свой деплой;
- добавлять источник в реестр.

Если тулу не хватает возможности каркаса, это отдельная задача на каркас, а не обход внутри тула.

**Run-time агент** работает внутри тула как шаг процесса и меняет данные. Собственных прав у него нет: он ходит через гейтвей с токеном тула. Запись возможна только по явному `writes` и после подтверждения человеком. В аудите отмечается, что агент участвовал в цепочке.

## Фасады UI

- **Web**: витрина `http://<tool>.tools.localhost:18000`.
- **MCP App** (официальное расширение MCP, SEP-1865): тул отдаёт UI как `ui://`-ресурс, его рендерит хост агента.

Бэкенд и токен у обоих фасадов общие, меняется только отдача UI. Свой UI-протокол не пишем.

## Стек и локальный стенд

- TypeScript, Node 22, npm workspaces. Один язык на всё; другие рантаймы и языки не добавляем.
- Docker Compose на одном хосте. Kubernetes вне итерации.
- Gitea + Gitea Actions — внутренний инструмент компании, CI живёт только там.
- Postgres — демо-источники `tasks` (доска задач команды), `knowledge` (база знаний, только дописывается) и `boards` (общие холсты тула whiteboard с историей версий). У каждого источника и каждого права записи своя роль БД с минимальными грантами.
- **Источники стенда и демо-слой разведены.** В `registry/sources.yaml` — источники этого стенда (их одобрил
  владелец данных), в `registry/demo/sources.yaml` — демо-слой платформы. Демо включается одним выключателем:
  `make demo-on` / `make demo-off` (`SANDBOX_DEMO` в `.env`) — от него зависят склейка реестра в гейтвее, налив
  демо-схем в Postgres и профиль compose `demo` с демо-коннекторами. Чистый контур — без источников вовсе.
- **Системы стенда — в своём файле compose.** Базы и коннекторы источников, которые подключил владелец данных,
  живут в `docker-compose.stand.yml` (подключается через `COMPOSE_FILE` в `.env`), а не в общем файле платформы.
  Наружу (`make public`) они не уезжают — как и тулы.
- Traefik — роутинг `*.tools.localhost` для витрины и превью веток.
- Вход — настоящий и для человека, и для агента: IdP компании, на стенде Keycloak (`auth.<домен>`), сервис
  `infra/identity` (`id.<домен>`) и ForwardAuth в Traefik. Агент входит через браузер человека (device flow),
  сессия лежит у него в `~/.sandbox`. Заголовок `X-Actor` больше ничего не значит.
- Реальные источники в эту итерацию не подключаются.

Порты не пересекаются со стандартными:

| Сервис | Порт |
| --- | --- |
| Gitea | 13000 |
| Gitea SSH | 12222 |
| Гейтвей | 18080 |
| Traefik (витрина `*.tools.localhost`) | 18000 |
| Главная страница песочницы | 18000, `http://tools.localhost:18000` |
| IdP стенда (Keycloak) | 18000, `http://auth.tools.localhost:18000` |
| Личность (вход, ForwardAuth, JWKS) | 18000, `http://id.tools.localhost:18000` |
| Postgres | не публикуется, сеть `data` internal; консоль через `make psql` |

## Как проверять изменения

- `make check` — контракт допуска и типы, то же, что CI.
- Перед следующим шагом плана и после правки каркаса — регресс по `docs/regress.md`; найденное записывается в
  `docs/roadmap.md`, раздел 0, а не чинится по-тихому.
- Изменение каркаса проверяется деплоем тула-примера: `make deploy TOOL=manager-board` и сценарии из README.
- Новый тул — только через `mcp-sandbox` (MCP-сервер `sandbox` в любом агенте) или `node infra/demo/sandbox-call.ts`.

## Правила работы

- Идём по шагам, после каждого человек может запустить и увидеть результат. Весь стенд разом не пишем.
- `main` в Gitea защищён: прямой пуш запрещён всем, мерж — только через PR после одобрения человеком из
  `sandbox-approvers` и зелёного CI; новые коммиты сбрасывают одобрение. Агент работает под ботом своего
  человека — `<логин>-agent`, доступ ему выдаёт сервис личности по личному ключу (шаг Б6): любая ветка,
  кроме `main`. Ветку проверяют до PR: после зелёного CI деплоер выкатывает превью затронутых тулов
  `<тул>--<ветка>.tools.localhost:18000`; ветку удалили — превью отзываются сами. Не пытайся обойти защиту
  учётной записью администратора из `.env`.
- **Превью не множатся.** Каждое превью — контейнер, образ и токен; держим их столько, сколько людей реально смотрит.
  - Тул — одно превью: `deploy_preview` всегда выкатывает `<тул>--preview` из ветки `preview/<тул>`. Не заводи для тула
    другие ветки, не пушь его в ветки каркаса.
  - Ветка каркаса превьюит тулы, только если меняет `packages/` (SDK, ui-kit) — тогда все тулы. Правки `gateway/`,
    `infra/`, `charts/`, `portal/`, `mcp-sandbox/` превью не дают: деплоер выкатывает своей копией каркаса.
  - Одна ветка каркаса за раз, от `main`. Следующую — после мержа предыдущей: ветка поверх неприлитой тянет её
    изменения и её превью. Если без неё никак — скажи человеку, что PR идут стопкой, и в каком порядке мержить.
  - Смерженная ветка удаляется сама; брошенную удали (`DELETE` ветки в Gitea) — превью отзовутся за минуту. Ветка без
    коммитов 7 дней считается брошенной: деплоер отзывает её превью сам. Проверка, что задача закрыта: `make tools`
    не показывает превью твоих веток.
  - На стенде не больше 10 живых превью (`GATEWAY_MAX_PREVIEWS`): сверх лимита гейтвей откажет в допуске со списком
    живых. Не обходи лимит — удали лишние ветки или спроси человека.
- Песочница на другом устройстве — только через `infra/install.sh` (архив — `make bundle`): переезжает платформа,
  тулы — нет. Не копируй между устройствами `tools/`, `.env`, тома Docker и историю git: у тула владелец, срок жизни
  и регистрация в гейтвее конкретного стенда; на новом стенде тул заводят заново через `mcp-sandbox`.
- Стенд слушает только `127.0.0.1`. `make lan` открывает его в локальную сеть — только по просьбе человека и только
  до настоящей авторизации (SSO — заглушка). Рабочая копия на другом устройстве — `infra/remote.sh`: в её `.env`
  только адрес стенда и учётка агента, команды стенда (`make up`, `deploy`, `backup`…) на ней отказывают. Не копируй
  туда `.env` сервера и не поднимай второй стенд; адреса бери из `SANDBOX_HOST`/`SANDBOX_DOMAIN`, не из `localhost`.
- Бэкап: `make backup` и `make backup-verify` агент запускать может; восстановление (`make restore`) — только человек
  в терминале, скрипт без TTY откажет. Бэкапы — только на внешнем диске или NAS (`SANDBOX_BACKUP_DIR`), ключ — у человека
  вне устройства. Не клади бэкапы и ключ в репозиторий и не добавляй в бэкап `.env`: секреты у каждого стенда свои.
  Тулы чужого стенда восстанавливаются только с `ADOPT=1` — это решение их владельца, не агента.
- **Наружу — только через `make public`** (`infra/publish.sh`): в публичный репозиторий уезжает платформа без
  `tools/`, без `.env` и без личных данных, и это проверяет сам скрипт — на находке он останавливается. Не пушь
  в интернет рабочую копию и историю git: в них код тулов и личные адреса. Скрипт ничего не отправляет: готовит
  каталог и печатает команды, публикует человек. Публичные файлы (лицензия, английский README, `SECURITY.md`) —
  в `publish/`.
- Правила для агентов живут только здесь. Не заводи копий в `.cursor/rules`, `CLAUDE.md` и т. п. — они разойдутся.
- Конфиги агентов (`.mcp.json`, `.cursor/mcp.json`, `opencode.json`) не правь руками: `make agents`.
- Валидация манифеста, проверка скоупа, сетевая изоляция и TTL работают по-настоящему. Заглушки допустимы только для SSO и внешних систем.
- Невозможность обойти гейтвей обеспечивается технически: сетью, отсутствием драйверов в SDK, проверкой зависимостей в CI. Соглашения здесь недостаточно.
- Не предлагать отвергнутое: ускорение продуктового цикла, прямой доступ агента к БД, low-code/PaaS, свой UI-протокол, песочницы по командам. Kubernetes и реальные источники предлагать только с объяснением, какую гипотезу это проверяет.

## Работа над тулом

Задача про тул — это работа внутри одной папки `tools/<slug>/`. У каждого тула есть свой `AGENTS.md` — прочитай его.

### Можно

- Менять `src/` (действия и логика) и `ui/` (интерфейс) своего тула.
- Менять `tool.yaml` своего тула — только в пределах реестра. Какие источники и права записи существуют,
  смотри через `list_sources` (MCP `sandbox`), а не угадывай. Нужного нет — скажи человеку: добавление
  источника в реестр решает он.
- Добавлять чистые npm-зависимости для вычислений и отображения.

### Как устроен тул

- Действие: `action({ description, input: { zod-схема }, handler })` из `@sandbox/sdk`. Оно доступно UI
  (`call()` / `useAction()`) и агенту в MCP-хосте как инструмент с тем же именем — пиши `description` так,
  чтобы агент понял, когда его вызывать.
- Данные — только `ctx.query(source, dataset, { fields, where, order_by, limit })`. Ответ может прийти урезанным:
  `redacted` — поля, скрытые по чувствительности, `row_scope` — какие строки человеку видны. Это нормально, покажи
  это человеку, а не считай пустоту данными. Операторы `where`:
  `eq, ne, gt, gte, lt, lte, in, contains`. Джойнов, агрегатов и OR нет — собирай в коде (запрос → `in` по id → `Map`).
  Не больше 1000 строк на запрос.
- Запись — только `ctx.prepareWrite(write, params)`. В UI (человек без агента) применяется сразу
  (`done`); важное действие (`confirm: true` в реестре) ui-kit сам покажет с «Подтвердить». С агентом — только
  подготовка: агент показывает человеку `summary` и после его согласия в чате вызывает встроенный
  `commit_approved`. Имена `commit_write`, `commit_approved`, `lifecycle*` зарезервированы каркасом.
- UI — Preact и компоненты `@sandbox/ui-kit` (`Page`, `Stats`, `Table`, `Tabs`, `Badge`, `Button`, `ErrorBox`,
  `useWrite`, `useMyWrites` — какие права записи разрешены этому человеку, чтобы не показывать лишние кнопки). Один UI работает и как веб-страница, и как MCP App — не пиши ветки под конкретный хост
  без `isApp`. Цвета — только CSS-переменные ui-kit (`--bg`, `--surface`, `--text`, `--accent`…), чтобы работали
  светлая и тёмная темы.
- Баннер срока жизни тула рисует `Page` сам — не дублируй его.
- Строка `# начат: …` в `tool.yaml` (ставит `scaffold_tool`) — начало работы для метрик на главной; не удаляй её.
- `title` и `description` тула и `description` действий показываются в каталоге на главной — пиши их для человека,
  который ищет тул под свою задачу.

### Нельзя

- Импортировать драйверы БД, `node:net`, `node:tls`, `node:dgram`, `node:child_process`, ходить `fetch` наружу:
  CI уронит сборку, а сеть тула всё равно видит только гейтвей.
- Писать авторизацию, токены, деплой, Dockerfile — это делает каркас.
- Менять что-либо вне `tools/<этот тул>/`, кроме `package-lock.json` после `npm install`.

### Цикл

`validate_manifest { name }` → коммит в рабочую ветку (`tools/<slug>`, `package-lock.json`, конфиги агентов) →
`deploy_preview { name }` → ссылка человеку → `get_logs { name }`, если что-то не так → когда человек доволен превью,
`open_pull_request { name, title, description }`. Одобряет и мержит PR человек; после мержа деплоер выкатывает прод.

## Задача на коннектор

Коннектор — сервис источника за гейтвеем. У него настоящие учётные данные и сетевой путь к системе: ошибка в нём —
ошибка у данных, гейтвей её не поймает. Поэтому правила строже, чем у тула. Берись, только если человек поставил задачу
именно на коннектор; из задачи про тул в `connectors/` не заходи — скажи человеку, каких данных не хватает.

### Можно

- Создать коннектор: `scaffold_connector { name, kind: sql | api | mcp, title, owner }` → `connectors/<имя>/`.
  `mcp` — MCP-сервер системы подключается файлом соответствий `config.yaml` (`startMcpConnector`), без кода.
- Писать `server.ts` / `config.yaml`: наборы данных и записи системы. Чтение базы — `sqlSelect`; API, файлы и MCP —
  `applyQuery`. Ошибка для человека — `ConnectorError(400 | 404 | 409)`.
- Набросать `registry.draft.yaml`: наборы, поля с чувствительностью, права записи (`confirm: true` — удаление,
  списание, всё необратимое; для MCP — инструменты с `destructiveHint`). Черновик — предложение, не решение.
- Тестовую систему в `test.ts` (+ `test/schema.sql` или `fixture/`): выдуманные данные той же формы, что в системе;
  **сценарий на каждое право записи** с проверкой, что изменилось только обещанное (`changes` для баз).
- Проверять: `validate_connector { name }` (`make validate-connector NAME=…`) — до зелёного, без предупреждений о
  записях без сценария.

### Нельзя

- Видеть, запрашивать и использовать боевые учётные данные, адреса боевых систем и боевые данные. Агент работает
  только с тестовой системой; адрес и учётка приходят из окружения, которое заводит человек.
- Переносить черновик в `registry/sources.yaml`, ставить `approved_by`, заводить токен коннектора, сервис и сеть
  в `docker-compose.yml` — это подключение источника, решение и работа человека (ИБ и владелец данных).
- Пробрасывать «всё API» или «все инструменты MCP-сервера»: каждый набор и каждая запись — отдельно, по одобрению.
- Делать в `describe` что-либо, кроме чтения; делать в `apply` больше, чем сказал `describe`.
- Запускать процессы, хранить секреты в коде, ходить на адреса, не объявленные в `hosts` теста, — это ловит
  `validate_connector`, но и без него нельзя.

### Цикл

`scaffold_connector` → `server.ts` / `config.yaml`, `test.ts`, `registry.draft.yaml` → `validate_connector` до
зелёного → коммит в рабочую ветку (`connectors/<имя>`, `package-lock.json`) → `open_pull_request { branch, … }` с
описанием: что за система, какие наборы и записи, что помечено `confirm`, чего не хватает от человека (учётка,
сеть, одобрение). Человек ревьюит код (прежде всего `apply`), одобряет источник, подключает.

## Изменение каркаса

Правка `gateway/`, `packages/`, `charts/`, `registry/`, `.gitea/`, `infra/`, `templates/`, `mcp-sandbox/` — задача на каркас, а не на тул. Убедись, что человек просил именно её; если ты пришёл сюда
из задачи про тул, остановись и предложи отдельную задачу.

### Правила

- **Реестр** (`registry/sources.yaml`) — решение человека (ИБ и владелец данных). Не добавляй источники и права
  записи по своей инициативе. Гейтвей перечитывает реестр сам: невалидный или без токенов и обработчиков не
  применяется, работает прежний, ошибка — в `/v1/registry` (`reload_error`).
- **Новый источник — коннектор** (`kind: connector`): сервис в `connectors/<источник>/` на каркасе
  `packages/connector`, запись в реестре, сервис и токен в `docker-compose.yml`/`infra/init-env.sh`, сеть только
  `sources`. Права записи — `source: <источник>`, сводку и запись делает коннектор. В `gateway/` строк не добавляется:
  скоуп, проверка параметров, `confirm`, двухшаговая запись и аудит — общие. Гейтвей не доверяет коннектору больше
  нужного: отдаёт только запрошенные поля и не больше лимита. Пример — `connectors/suppliers`, проверка — `make demo-connector`.
- **Источники Postgres стенда** (задачи, знания, доски, кондитерская) — коннектор `connectors/postgres`: экземпляр на
  источник, описание источника (таблицы, колонки, роли, обработчики записи) — `connectors/postgres/src/sources/<источник>.ts`.
  Новое право записи здесь — роль БД с минимальными грантами (`infra/postgres/init/02-roles.sh`), пароль в
  `infra/init-env.sh` и в окружении **этого коннектора** в `docker-compose.yml`, обработчик в файле источника, запись в
  реестре с `source`. У гейтвея паролей ролей источников нет и не должно быть.
- **Невозможность обойти гейтвей обеспечивается технически**: сетью (`data`, `tools`, `sources` — internal), отсутствием
  драйверов в SDK и проверкой зависимостей в `packages/manifest/src/cli.ts`. Не ослабляй ни одно из трёх.
- **CI только проверяет, выкатывает деплоер.** Workflow берётся из ветки, поэтому у джобы нет секретов, сокета
  Docker и сети с гейтвеем (`infra/runner/config.yaml`: `docker_host: "-"`). Не возвращай деплой в
  `.gitea/workflows/` и не заводи секреты CI: выкатка — только `infra/deployer` своим кодом после зелёного CI.
- **Сервисные токены гейтвея — по роли** (`admin`, `deployer`, `reaper`, `portal`, `notifier` в `gateway/src/config.ts`).
  Новому сервису — новая роль с минимальным набором прав, а не общий админ-токен.
- **Запись** — решение человека, и аудит говорит правду, кто был в цепочке:
  - UI (человек без агента): клик в форме — решение, `apply` пишет сразу. Важное действие (`confirm: true` в
    реестре: удаление, списание) гейтвей не применяет сразу — возвращает `summary`, человек жмёт «Подтвердить»
    (`commit_write`, только UI: `visibility: app`, модели не виден).
  - Агент: только `prepare`. Показывает человеку `summary`, ждёт явного согласия в чате и применяет
    `commit_approved` с ответом человека дословно. Гейтвей пускает агента только к подготовленному агентом,
    без `approval` отказывает, в аудите — `agent_in_chain` и цитата согласия.
  - До настоящей авторизации «ждать согласия» держится на агенте и запросе разрешения инструмента в хосте —
    не ставь `commit_approved` в «всегда разрешать». Любой новый путь записи обязан сохранить это и писать
    аудит (`audit.calls`), включая отказы, — до записи.
- **Личность — только подписанная.** Человек доказывает, кто он, один раз в IdP; дальше каждый запрос несёт
  `X-Sandbox-Identity` — короткий JWT от `infra/identity` с `sub`, `groups`, `channel` и `aud` ровно того инстанса,
  куда идёт запрос. Traefik вырезает этот заголовок у клиента и ставит свой. Тул личность не придумывает и не
  проверяет — только пересылает в гейтвей; проверяет подпись, издателя, срок и `aud` гейтвей
  (`gateway/src/identity.ts`). В новом коде не читай `X-Actor` — его больше нет. Канал личности (`web` или `mcp`)
  решает, можно ли подтвердить запись самому: из браузера — да, из хоста агента — только с согласием человека.
- **Справочник** (`registry/directory.yaml`) — заглушка HR/IdP до шага Б1 и, как реестр, решение человека: агенты
  его не правят. Кто решает за владельца (продлить, удалить, получить уведомление) — только `ownersOf` в гейтвее:
  ушёл — руководитель, группа — участники, никого — тул сразу в простой, решают `sandbox-admins`. Не сравнивай
  `actor === owner` в новом коде — бери `owners` из гейтвея (`/v1/admin/tools`, `lifecycle`).
- **Права на данные — решение гейтвея по реестру** (`gateway/src/query.ts`, `writes.ts`). Чувствительные поля
  (`field_groups` источника: уровень → группы) человеку вне этих групп приходят пустыми и перечислены в `redacted`;
  строки фильтруются `row_filter` набора (поле, группа → значения, `unrestricted_groups`), и охват виден в
  `row_scope`. Право записи можно сузить группами в манифесте; гейтвей проверяет это и на `apply`, и на `commit`.
  Всё это — решение хранителя данных в реестре, а не тула: тул не может расширить себе видимость.
- **Доступ к тулу — решение гейтвея** (`gateway/src/access.ts`, таблица `gateway.tool_access`). Проверка стоит
  дважды: ForwardAuth отказывает до тула, гейтвей повторяет её на вызове (тул могли позвать изнутри сети). Владелец
  и администратор песочницы — всегда; превью смотрят владелец и одобряющие, а не все группы тула. Источник
  ограничивает круг через `allowed_groups`: это решение хранителя данных, а не владельца тула.
- **Группы — решение гейтвея** (`gateway/src/groups.ts`, таблицы `gateway.groups`, `gateway.group_members`).
  Две породы: зеркало IdP (отдел, должность) приходит в личности и правится в IdP; группы песочницы заводит
  администратор (`sandbox-admins`) на главной, и меняются они только через API гейтвея — он проверяет права и
  пишет аудит. Участие может быть срочным; просроченное не действует. Сервис личности складывает обе породы в
  личность, кэш — минута, поэтому исключение из группы действует на следующем вызове.
- **Ключ MCP — у человека, а не у тула** (`infra/identity/src/keys.ts`, схема `identity` со своей ролью БД).
  В базе только префикс и хэш секрета; сам ключ показывается один раз в кабинете `/me`. Права в ключ не зашиты:
  группы перечитываются на каждом вызове, поэтому при смене групп ключ не перевыпускают. Отзыв действует сразу.
  Ключ не должен попадать ни в логи, ни в аудит — только префикс. Новый путь входа обязан это сохранить.
- **Уведомления** — только через `infra/notifier` (`POST /notify` с токеном отправителя, `key` — событие доставляется
  один раз). Кому — пишешь как в справочнике (логин, группа, e-mail автора коммита), кому на самом деле — решает
  справочник. Уведомление не должно ломать основную работу сервиса: ошибка — в лог, повтор на следующем цикле.
  Канал на стенде — входящие на главной; мессенджер или почта компании — решение человека (roadmap, раздел 5).
- **Срок жизни**: автопродление только от вызовов человека и не дальше `max_ttl_days` от последнего явного
  продления; простой → уведомление → удаление. Продлить и удалить из UI может только тот, кто решает за владельца.
- **Схема БД** инициализируется только на пустом томе. Меняешь `infra/postgres/init/*` — дай команду миграции
  для живого стенда (`make psql`) или явно предупреди, что нужен пересоздаваемый том.
- **Совместимость тулов**: встроенные в каркас возможности должны появляться в тулах без правки их кода.

### Проверка

Изменение каркаса — в своей ветке, как и тул: пуш → CI → деплоер выкатывает превью всех тулов на коде ветки → проверка →
`open_pull_request { branch, title, description }` → одобрение и мерж человеком. Гейтвей, Postgres, деплоер и уборщик на
стенде общие: их изменения ветка не превьюит — проверяй локально (шаги ниже) до PR.

1. `make check` — контракт допуска и типы.
2. Пересборка: `docker compose up -d --build --wait gateway`, при изменении деплоера или `charts/tool-base` —
   `docker compose up -d --build deployer` (он выкатывает своей копией каркаса), уборщика — `docker compose restart reaper`.
3. `make deploy TOOL=manager-board` и сценарии из README; для гейтвея — `make demo-gateway`,
   для MCP-фасада — `node infra/demo/mcp-app.ts`.
4. Обнови этот файл и README, если меняются правила или сценарии.

## Подключение агентов

Все агенты запускают один `bin/sandbox-mcp`; конфиги в репозитории, их генерирует `make agents`
(и `scaffold_tool` — новый тул сразу виден всем агентам как `sandbox-<имя>`).

| Агент | Правила | MCP |
| --- | --- | --- |
| Claude Code | `CLAUDE.md` → `@AGENTS.md` | `.mcp.json` (одобрить серверы проекта при первом запуске) |
| Cursor, `cursor-agent` | `AGENTS.md` | `.cursor/mcp.json` (включить в Settings → MCP) |
| OpenCode | `AGENTS.md` | `opencode.json` |
| Codex и другие | `AGENTS.md` | вручную: команда `<репо>/bin/sandbox-mcp platform` и `… tool <имя>` (stdio) |

- `sandbox` — build-time: создание и выкатка тулов. `sandbox-<тул>` — run-time: данные тула через его токен.
- **Build-time тоже требует личного ключа** (шаг Б6): `bin/sandbox-mcp login` один раз, дальше сервер сам
  обменивает ключ на короткоживущий токен бота `<логин>-agent`. Нужна группа `sandbox-developers` — без неё
  сервис личности отказывает с объяснением. Учётных данных Gitea на машине разработчика больше нет:
  `GITEA_AGENT_*` в `.env` рабочей копии не кладётся, а `make lan` печатает команду с ключом, а не с паролем.
- Кто вы для run-time решает IdP: `bin/sandbox-mcp login` один раз открывает браузер и кладёт личный ключ
  в Keychain (иначе — файл `~/.sandbox`, либо переменная `SANDBOX_MCP_KEY`). Дальше `bin/sandbox-mcp tool <имя>`
  работает без браузера; без ключа мост сам предложит вход. Логин аргументом не передаётся.
- Запись через MCP: агент вызывает действие → получает `summary` и `confirmation_id` → показывает `summary`
  человеку и ждёт «да» в чате → `commit_approved` с ответом человека. В web UI второй шаг нужен только для
  важных действий (`confirm` в реестре).
