# Правила для агента в этой папке

Это тул песочницы. Контракт — `tool.yaml`, каркас — `@sandbox/sdk` и `@sandbox/ui-kit`.

## Можно
- Менять `src/` (логика, действия) и `ui/` (интерфейс).
- Менять `tool.yaml` в пределах реестра: источники и права записи — только из `list_sources` (mcp-sandbox).
- Добавлять чистые npm-зависимости для вычислений и отображения.

## Нельзя
- Ходить к данным мимо `ctx.query` / `ctx.prepareWrite`. Драйверы БД, `child_process`, `net`, `tls` — CI уронит сборку, а сеть тула всё равно видит только гейтвей.
- Писать свою авторизацию, деплой, Dockerfile, работу с токенами — это делает каркас.
- Менять что-либо вне `tools/<этот тул>/`: `packages/`, `charts/`, `gateway/`, `registry/`, `.gitea/`. Не хватает возможности каркаса — это отдельная задача на каркас.
- Применять запись без явного согласия человека в чате. Через MCP действие только готовит: покажи человеку `summary` дословно, спроси и лишь после «да» вызови `commit_approved { confirmation_id, approval: <его ответ дословно> }`. В UI запись идёт сразу (`useWrite`), важное действие (`confirm` в реестре) — после «Подтвердить».

## Как устроено
- Действие = `action({ description, input: {zod-схема}, handler })`. Оно доступно UI (`call()` / `useAction()`),
  а агенту в хосте с MCP — как MCP-инструмент с тем же именем.
- UI один на два фасада: web-страница `<tool>.tools.localhost` и MCP App в хосте агента.
- Цикл: `validate_manifest` → коммит → `deploy_preview` → ссылка человеку → `get_logs`, если что-то не так.
